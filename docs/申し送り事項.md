# 申し送り事項

本書は、**コードと設計ドキュメントを読んでも分からない背景**を残すためのものである。担当者やツールが変わっても、同じ検討を一からやり直さずに済むようにする。

**本書は仕様ではない。** 仕様の正は `要件定義書.md` / `ユースケース設計書.md` / `テーブル定義書.md` にあり、その変更経緯は `改訂履歴.md` にある。本書が扱うのは次の5つ。

1. 進め方の合意（開発の手順そのもの）
2. **検討して却下した案とその理由** — 再提案を防ぐため、本書で最も重要な節
3. 暫定実装と、最終的にどうするか
4. 技術的な決定と、実際に踏んだ罠
5. 既知の残件

最終更新: 2026-09-08

---

## 1. 進め方の合意

### 1機能=1セッションで進める

作業は**1つの機能ごとに区切って進める**（2026-07-29 合意）。着手時はまず機能名を決め、関連する設計ドキュメントと該当コードを読んでから手を動かす。文脈を絞ることで実装もレビューもしやすくなるため。

大きめの機能は**計画を提示して合意を取ってから実装する**。

### 区切りごとにコミットする

サブフェーズが問題なく終わった時点で、指示を待たずにコミットする（2026-07-17 合意）。区切りごとに履歴が残るほうが、卒業研究として実装の経緯を追いやすく、レビュー単位とも一致するため。

ただし**UIを伴う変更は、実機での確認でOKが出てからコミットする**。型チェック・Lint・テストが通っているだけでは足りない。

### 仕様に無いことは勝手に決めない

本プロジェクトは未定義事項を潰してから実装に入っている。そのため「仕様に書いていない」と感じたときは、**たいていドキュメントの読み落とし**か、**本当に新規の検討事項**のどちらかである。前者なら探せば見つかるし、後者なら人間に相談すべきものなので、いずれにせよ推測で埋めてはいけない。

## 2. 検討して却下した案

**ここに挙げた案は、一度検討したうえで意識的に見送ったものである。** 再提案する前に理由を読むこと。ユーザー側から言い出した場合は別。

### メモの見返し機能 — やらないと確定

メモは500文字書けて日別詳細に出るが、読み返す手段がカレンダーで日付を1つずつ開くことしかない。この課題は認識したうえで、**2026-08-08 に「やらない」と確定した**。一度は実装方針まで決めたが、着手前に取りやめている。**候補として再提案しないこと。**

（経緯として、採用しかけた案は「ふりかえりタブの末尾にその月のメモを並べる」「日別詳細を記録のある夜だけ前後に送れるようにする」の2つ。却下したのは「タグ集計から辿る」＝実質的に新画面が増えるためで、ユーザーは「専用機能を新しく追加するのは避けたい」と明言していた。）

### ホームに物を増やす

アルバムの演出をどこに出すか検討した際、**ホームに要素を足す案は却下された**。「ホームは静けさ自体が価値」というユーザーの判断による。

このため**街の見た目が変わる条件はレベル（学習時間）だけに保つ**。演出はカレンダー側に出した。

### アルバムを「収集対象」にする

夜の天気アルバムの演出条件に**天気の種類数を使う案は却下**し、「学習した夜の数」にした。`n/11種` のような表記も削除済み。

理由は2つ。揃っていない種類を見せると、**その夜の実感ではなく空欄を埋めるために天気を選ぶ**動機が生まれ、記録が事実でなくなること。もう1つは、地域や季節によって出会えない天気があり、進みが運任せになること。

### 段階の数値を画面に出す

アルバムの演出段階は**画面に数値として出さない**。出すと段階を上げること自体が目的になるため。

また**1段階目を「飾りが剥がれた見た目」にしない**。夜が少なかった月を欠けた見た目にすると、「サボった月」を突きつける形になる。1段階目は現行のカードそのままで、2段階目以降がささやかな上乗せになる設計。

### 連続日数・達成率・平均の推移

いずれも**足りないことの可視化**になるため却下。コンセプト（急かさない・責めない・競わせない）に反する。

### 写真をアルバムに混ぜる

要件定義書で明記済みの方針として却下。欲しくなった場合は別立ての新規仕様として相談する。

### 夜の写真のピンチ拡大

**一度実装して外した。** 夜空は細部を見る被写体ではなく、保存時に長辺1280pxまで縮めているため、寄っても粗さが出るだけだった。

### 夜の写真を「空／外」の2種類にする

却下。**1学習日につき1枚**とした。

### 通算100夜を演出のしきい値にする

却下。実データで到達する前にアプリを使う期間のほうが終わり、演出が働かないため。現在のしきい値は月次5/15夜、通算20/60夜。

### アルバム演出の見た目で試して外したもの

- **枠線** — カードの枠と二重になり、仕切りに見えた
- **星を帯に押し込む** — 一列に並んで見えた

### 設定に「夜の写真のON/OFF」を置く

**廃止した**（要件は欠番）。撮影を選ばない限りカメラ権限を要求せず写真も保存されないため、この設定が防ぐものが無い。カメラと無縁でいたい人への配慮は、設定ではなく仕組み側で保証するほうが強い。

なお `user.night_photo_enabled` の列は**未使用のまま残してある**。落とすマイグレーションは配布済み端末へのリスクに見合わないため。

### 月次ふりかえりで一度作って外したもの

- **月ごとの推移** — 月で区切るのは月次タブの役割と重複する
- **通算の最頻感情** — 数か月で固定表示になり、人へのラベルになってしまう
- **「いつからの記録」表示** — 情報として不要だった

## 3. 仕様上の判断とその理由

### 休憩提案の基準に「今回の予定学習時間」を足す

最初の休憩提案の基準は `max(一日の目標時間, セッション開始時点の実績合計 ＋ 今回のセッションの予定学習時間)`（2026-07-23 変更）。

目標が60分でも、ユーザーが今回90分と設定したなら**その90分は自分で決めた学習時間**である。途中の60分で休憩提案が割り込むのは「急かさない・責めない」に反して面倒、というのが理由。開始時点の実績も足すことで、複数セッション目でも今回決めた分を丸ごと邪魔しない。

予定学習時間の算出は黙々=設定分数、ポモドーロ=作業時間×回数で**2モード統一**。純関数 `getInitialBreakThreshold()`（`src/lib/break-suggestion.ts`）に集約してテスト済み。

**目標達成（経験値・成長）の判定は別物**で、こちらは従来どおり一日の目標時間で判定する。休憩基準の変更は経験値に影響しない。

### 昼間（5:00〜17:59）の学習日帰属は暫定のまま

`getStudyDate`（`src/lib/study-day.ts`）は要件0章で未定義な昼間の帰属を、暫定で「これから始まる夜のサイクル＝当日」としている。**この暫定のまま進めてよい**という判断（2026-07-16）。

セッションは夜間帯しか開始できないため帰属ロジック自体に実害がなく、天気入力UI上に学習日の日付を表示してユーザーに明示する方針としたため。**`getStudyDate` の昼間分岐は変更しないこと。**

### 成長方式は初期設定で選ばせない

習慣型／プロジェクト型の選択を初期設定に入れる案は却下（2026-07-16）。setup前にこの概念を選ばせるとオンボーディング負荷が高く、chillな第一印象を損なうため。

代わりに**初回ホーム表示で一度だけ「育て方のお知らせ」カード**を出す。ボタンは「わかった」1つのみで、**その場での切替は持たない（情報提示のみ）**。切替UI本体は設定画面にある。表示済みフラグは `user` テーブルに永続化。

### 夜の写真は「撮影 → 天気」の順

この順序にしたため、`night_weather_id` を**NULL許容**にしてある。天気未選択の判定が「行の有無」から「列のNULL」に変わっている点に注意。

タブUIは不採用（天気を選ぶと選択欄が閉じる既存挙動と噛み合わないため縦2段にした）。帰属は**撮り始めた時刻の学習日**。「0時以降は翌日に」という案も出たが、天気と写真が別の夜に割れて1晩2枚持ててしまうため却下し、**学習日基準のまま実際の撮影時刻を表示**して違和感を解消した。学習日の定義自体は変えていない。

### 撮影中はBGM・環境音を自前で止めて戻す

`AudioContext.runAndRestoreAudio` で明示的に制御している。OS任せにすると iOS（カメラをアプリ内に重ねるので鳴り続ける）と Android（別画面なので止まる）で挙動が割れるため。

### 月次ふりかえりの声は「いまの街の住人」

カレンダーを開いている時点で選択中の街の住人が振り返る。過去の月を見ても声は現在の住人のもので、街を切り替えると声が変わる。

文面は `src/lib/monthly-review.ts` 側に持ち、**DBには入れていない**（月次メッセージは表示専用と要件に明記されているため）。

### 住人の口調は互いに重ならないよう選んである

8人ぶんの文面があり、語尾や一人称が既存の人物と重複しないように設計している。変えるとこの設計が崩れるため、口調を触るときは全員を見渡すこと。

### 通知文面を通知時刻で出し分ける

- **17:30〜17:59**: 「夜が目覚めるまであと◯分」のカウントダウン文面
- **18:00〜翌4:30**: 通常の学習開始リマインド文面

18:00前はまだタイマーを開始できないため、開始を促すのではなく夜の開始までを伝えるほうがコンセプトに合う。◯分はスケジュール登録時に静的に確定できる（毎日固定なので動的計算は不要）。

### 休憩提案の音に鐘を使わない

鐘は終了演出の音であり、1晩で2回鳴ると意味が混ざるため。休憩提案は効果音（`break_notice`）として別に持つ。

## 5. 技術的な決定と踏んだ罠

### Expo SDK 57（2026-09-07 移行）

SDK 54 から上げた。Expo Go が SDK 57 化し、**Expo Go は最新SDK 1つしかサポートせず iOS は旧版に戻せない**ため、実機確認の手段を保つには追従するしかなかった。

移行で踏んだ変更のうち、再発しうるものは `開発環境_導入手順書.md` のトラブルシューティングに載せてある。とくに次の2点は**型エラーにならないので気づきにくい**。

- **`File.move()` / `copy()` が SDK 56 から非同期**（`delete()` / `create()` は同期のまま）。`await` を忘れても浮いた Promise は型違反ではないため検出されない。`night-photo-storage.ts` で実際に漏れており、「保存の成功後にDBを更新する」順序が崩れて**実体のない参照が記録に残りうる**状態だった
- **`expo-asset` は直接依存に入れる**。無いと `expo-modules-core` が入れ子配置になり、`AudioPlayer.addListener` などの型解決が失敗する

`expo-router` は SDK 56 から `@react-navigation/*` に依存しなくなった。`useIsFocused` / `ThemeProvider` / `DarkTheme` / `DefaultTheme` は **`expo-router` から import する**。

### React Compiler 系の ESLint ルールを3つ外してある

`eslint.config.js` で `react-hooks/immutability` / `set-state-in-effect` / `preserve-manual-memoization` を **意図的に off にしている**（理由は設定ファイル内にも記載）。

- `immutability` … Reanimated の `SharedValue.value` と expo-audio の `AudioPlayer.volume` / `.loop` への代入を検出する。**どちらも書き換えるために存在するオブジェクトで、代入以外に設定手段がない**
- `set-state-in-effect` … 該当は「非同期のデータ読み込み」と「モーダルを開くたびの値リセット」の2種のみで、どちらも意図した形
- `preserve-manual-memoization` … 「Compilation Skipped」の報告。手書きの `useCallback` はそのまま効いており、正しさの問題ではない

**同時に検出された `react-hooks/refs`（25件）は外さず実際に直している。** レンダー中の ref 読み書きは React Compiler が扱えないため、これは直す価値があった。新しく書くコードでも**レンダー中の ref 読み書きは避けること**。

「lint を厳しくしよう」という提案が出たら、まずこの節を読むこと。

### マイグレーションの注意

**`SCHEMA_VERSION` は `DELTA_MIGRATIONS` の最後の version と必ず一致させる。** 一度ずれた状態で放置され、新規インストールが2回目の起動で落ちる状態になったことがある（最新形のスキーマ＋古い user_version の組み合わせで、適用済みの ALTER が duplicate column で再実行される）。**既存端末では再現しないため気づきにくい。**

NPCの文面を直したときは、`docs/NPCセリフ集.md`（文面の正）を編集 → `npm run npc:seed` の順。**配布済み端末へ届けるには、シードを流し直すだけの版をマイグレーションに1つ足して `SCHEMA_VERSION` を +1 する。**

### Expo Go はログインが必須（SDK 57 以降・iOSのみ）

パソコン側（`npx expo login`）とスマホ側（Expo Go 右上のアバターアイコン）の**両方**でログインしていないとプロジェクトを開けない。設定ミスと紛らわしいので、詰まったら `開発環境_導入手順書.md` の 1.5 を見ること。

あわせて、**Expo Go の履歴（Recently opened）からタップしない。** 古い接続先が残っていると、いま起動したサーバーではなくそちらへ繋ぎに行き、原因の分かりにくいエラーになる。

### Expo Go では確認できない機能

**BGM・環境音のバックグラウンド再生**と**ロック画面の再生コントロール**は Expo Go では動かない。config plugin はビルド時にしか効かず、Expo Go のバイナリには反映されないため。「実装が間違っている」と誤診しやすい。

一方、**ローカル通知は Expo Go でも動く**。

確認するには development build が要る。iOS 版は Windows では作れず（Xcode が必要）、EAS Build + Apple Developer Program（年$99）が必要。**Android 版なら Windows から EAS Build で作れて追加費用も要らない。**

## 6. 既知の残件

### プレイリストの高速切替がまれに不発

曲を人力で高速に交互タップすると、たまに音だけ切り替わらない（描画とタップは正常）。

**切り分け済みの事実:**
- 全タップが `pressIn → press → playTrack → load+play` まで通っており、**タッチ落ちではない**
- 最大の原因だった「切替のたび2.5秒フェードで音量0から始まり無音に感じる」問題は解決済み
- 120msの間引き（trailing debounce）は、速く叩き続けるとタイマーが発火せず切り替わらなくなる（starvation）ため撤去済み
- 残るのは expo-audio の `player.replace()` を高速連打したときの**エンジン側の競合**と推定

**試してダメだったので戻した対策:**
- `TrackRow` の memo 化 → 悪化（revert 済み）
- 曲ごとにプレイヤーをキャッシュし、切替を replace からプレイヤー入れ替えに変更 → **さらに悪化**（revert 済み）

**次に試す候補:** プレイヤーキャッシュ方式の作り直し（前回は進捗リスナーの張り替えと頭出しの副作用で悪化した疑い）／`replace` 後の `play` を `isLoaded` を見てから呼ぶ状態機械／expo-audio のバージョン差確認。**着手前に実機で再度切り分けること。**

### 後回しと決めてあるもの

以下は**プロジェクトの最後の方に回す**と決めてある（2026-07-23）。先に機能実装を進める。

- **未制作の音**: ポモドーロのフェーズ切替音（`pomodoro_phase`）・UI操作音（`ui_tap`）・休憩通知音の最終素材（`break_notice`）・天気11種の環境音。いずれも鳴らす経路は実装済みで、素材を足すだけ
- **背景の時間帯差分画像**: できたら `townArt.ts` に時間帯キーを足す
- **実機での通し確認**: とくに通知は development build が要る

### 検証が済んでいないもの

- **保存後の写真ファイルに EXIF/GPS が残っていないかの実物確認**（セキュリティ方針のリリース前チェックリスト）
- **BGMのバックグラウンド再生とロック画面コントロール**（実装済みだが Expo Go では確認できない。Android の development build を作れば検証できる）
- **カレンダーの星・流れ星の演出**が正しく出ているか。「出ないことがある」という報告があるが、**その月が5夜未満なら設計上そもそも描画しない**ため勘違いの可能性が高く、確定していない

### チームに依頼中で待ちのもの

2つ目以降の街の背景と、天気演出の残り素材。**ユーザーが自分でやれば早いが、チーム開発として任せる判断をしている。** これらが揃っている前提の提案はしないこと。

## 7. 開発中の作業ブランチ

`main` 以外にブランチがある場合、実機確認が済んでいない作業が載っていることがある。着手前に `git branch -v` で確認すること。

2026-09-08 時点では `feat/weather-ambient` に、天気の環境音とBGMライブラリ再編の作業が**実機未確認のまま**載っている。環境音4本（雨・雷入りの雨・夜風・虫の音）と天気コードの対応は `src/lib/ambient-select.ts` の `WEATHER_TO_AMBIENT` にある。

このうち**嵐の夜は、映像に雷を使わず環境音側で雷らしさを出す**方針にしてある。雷単体に対応する天気コードが無いため（`assets/未使用/README.md` 参照）。
