# セキュリティ方針

本アプリで**何を脅威とみなし、何を対策し、何を対象外としたか**をまとめる。

一般的なセキュリティチェックリストをそのまま適用するのではなく、**本アプリの構成から成立し得ない脅威を除外し、残ったものに対策を割り当てる**という順序で記述する（卒業研究として「なぜその対策なのか／なぜそれをやらないのか」を説明できるようにするため）。

実装状況は「3. 対策一覧」の状態欄が正。リリース前に「6. リリース前チェックリスト」を消化すること。

- 記載時点: 2026-08-01（schema v22 / Expo SDK 54）
- 関連: `docs/chill_night_town_要件定義書_v2.md`（10.10 データ初期化・12章 通知）／`docs/開発用テストボタン.md`（撤去対象の一覧）

## 1. 前提となる構成

本アプリは**サーバーを持たない完全ローカル構成**であり、これがセキュリティ上の性質をほぼ決めている。

| 項目 | 本アプリ | セキュリティ上の意味 |
| :---- | :---- | :---- |
| サーバー・API | なし | サーバー側の攻撃面が存在しない |
| 外部通信 | なし | 通信の盗聴・改ざんが成立しない |
| 認証・アカウント | なし | 認証情報の漏洩・なりすましが成立しない |
| 個人識別情報 | ニックネームのみ（任意の文字列） | 本名・メール・電話番号等を一切保持しない |
| データの保存先 | 端末内 SQLite 1ファイル（アプリ専有領域） | 保護の主体は OS のサンドボックス |
| WebView | なし | XSS・任意コード実行の経路がない |
| 外部ファイルの取り込み | なし（音源・画像はすべてバンドル同梱）。**ただし利用者自身が撮影した写真をアプリ専有領域へ保存する**（要件2.6） | 第三者が用意したファイルを読み込む経路は無い。写真は利用者自身が生成したデータであり、外部へ出ることもない |
| 権限要求 | ローカル通知 ＋ **カメラ（任意・設定でOFFにできる）** | マイク・位置情報・連絡先・外部ストレージ（写真ライブラリを含む）は要求しない。カメラは「夜の写真」（要件2.6）でのみ使い、**設定OFFなら一度も要求しない** |

**補足**

- `src/db/sql-loader.ts` に `fetch` があるが、これは**バンドル同梱の `.sql` アセットを読むためのもの**で、外部ホストへは接続しない（Expo のアセット解決が返すローカル URI を読む）
- したがって「ネットワーク越しの攻撃者」というアクターは本アプリには存在しない。現実的な脅威は**端末を触れる人間**と**自分たちが混入させる欠陥**の2系統に絞られる

## 2. 脅威モデル

### 2.1 守るべき資産

| 資産 | 内容 | 機微度 | 理由 |
| :---- | :---- | :---- | :---- |
| 振り返りメモ | 学習後に自由記述する最大500文字 | **高** | 利用者が私的な心情を書きうる。本アプリで最も機微な情報 |
| その夜の写真 | 学習日ごとに1枚、利用者がカメラで撮影した画像（要件2.6） | **高** | 意図せず室内・家族・人物・自宅周辺の風景が写り込みうる。テキストと違い**撮った本人が想定していない情報まで含む**点でメモとは性質が異なる。撮影時刻とあわせて生活パターンも読み取れる |
| 感情記録 | セッションごとの感情の選択（11種） | 中 | 精神状態の推移が読み取れる |
| 学習記録・カレンダー | 学習日ごとの実績時間・天気・タグ | 中〜低 | 生活時間帯（深夜に起きている等）が推測できる |
| ニックネーム | 最大20文字 | 低 | 本名である必要がなく、他情報と結びつかない |
| 設定値・街の進捗 | 目標時間・成長方式・レベル等 | 低 | 単体では意味を持たない |

**本アプリのセキュリティ上の要点は「メモ・写真・感情の秘匿」であり、それ以外は可用性・完全性（記録が壊れないこと）の問題として扱う。**

> **補足（写真機能の追加による方針変更）**: 要件2.6「今夜の写真」を追加するまで、本アプリはカメラ権限を要求せず、利用者が生成する非テキストのデータを一切持たなかった。写真は**守るべき資産の性質を変える**（写り込み・位置情報・削除要求への対応）ため、資産・脅威・対策を本方針に追記した。写真を扱わない選択（設定OFF）を必ず残すのは、この資産を持ちたくない利用者に持たせないための設計である。

### 2.2 想定する脅威

| ID | 脅威 | 具体例 |
| :---- | :---- | :---- |
| **T1** | 端末を物理的に操作できる第三者 | 家族・友人がアプリを開いてメモを読む。端末の紛失・譲渡 |
| **T2** | 端末外へのデータ流出 | ロック画面通知の覗き見。ログや Git 履歴への個人データの残留 |
| **T3** | 開発用コードの本番混入 | `__DEV__` 判定の誤りや撤去漏れにより、データ削除・レベル操作の機能が利用者に露出する |
| **T4** | 依存パッケージ由来の脆弱性 | npm パッケージの既知脆弱性・サプライチェーン汚染 |
| **T5** | 写真に付随する意図しない情報 | 撮影した画像の EXIF に撮影位置（GPS）が埋め込まれ、端末を触れる第三者や、将来の書き出し機能に自宅の座標が伴う。写り込んだ室内・人物が本人の意図せず残り続ける |

**T3 が本アプリで最も現実的なリスク。** `src/db/repositories/devRepo.ts` は学習記録の削除・マスタの書き換え・要件6.1「レベルは下がらない」を意図的に破る操作を持ち、露出すれば利用者のデータを直接壊す（詳細は `docs/開発用テストボタン.md`）。

### 2.3 想定しない脅威と、その理由

| 想定しない脅威 | 理由 |
| :---- | :---- |
| ネットワーク上の攻撃者（盗聴・改ざん・中間者） | 外部通信を一切行わないため成立しない |
| 他ユーザーによる不正アクセス・権限昇格 | サーバーもマルチユーザー機能も持たない。1端末1利用者 |
| root 化・脱獄済み端末上の攻撃者 | OS のサンドボックスという保護の前提が崩れる。これに抗するには DB 暗号化等が必要だが、**個人の学習記録に対しては費用対効果が見合わない**ため、リスクとして受容する |
| 同一端末上の悪意ある他アプリ | OS のアプリ間サンドボックスに委ねる。アプリ専有領域は他アプリから読めない |
| 大量アクセス・DoS | 攻撃対象となるサーバーが存在しない |

## 4. 各対策の詳細

### S1. 開発用コードのリリース前撤去（T3）

| 項目 | 内容 |
| :---- | :---- |
| 目的 | 開発用の破壊的操作が本番ビルドに露出することを防ぐ |
| 現状 | すべて `__DEV__` で分岐しており、本番ビルドでは表示・実行されない。ただし**コードは残っている** |

**内容**

- 撤去対象と手順は `docs/開発用テストボタン.md` の「撤去チェックリスト」を正とする
- `__DEV__` による分岐は一次防御にすぎない。**フラグ1つの書き間違いで露出する構造は残さず、ファイルごと削除する**のが正しい対処
- 撤去後、`__DEV__` の残骸が無いことを検索で確認する

```
grep -rn "__DEV__\|devRepo" src/
```

**関連する注意点**

- `src/lib/clock.ts` の時刻オフセットは、本番ビルドでは `nowMs()` が実時間を返す実装になっている（`__DEV__ ? devOffsetMs : 0`）。ただし**時刻を操作できる仕組みが本番コードに残ること自体を避ける**ため、撤去対象に含める
- `setHabitLevelStep()` はマスタ（`growth_level_threshold`）を書き換える。**マスタはデータ初期化では戻らない**ため、テストに使った端末が本番の閾値に戻っているか撤去時に確認する

### S2. SQL はプレースホルダのみで組み立てる（完全性）

| 項目 | 内容 |
| :---- | :---- |
| 目的 | 利用者の入力（ニックネーム・タグ名・メモ・予定タイトル等）が SQL として解釈されることを防ぐ |
| 現状 | **全リポジトリで対策済み** |

**内容**

- すべてのクエリで値は `?` にバインドしている。文字列連結・テンプレートリテラルによる値の埋め込みは行っていない
- 現在テンプレートリテラルを含む SQL は次の2箇所のみで、いずれも利用者入力を含まない：

| 箇所 | 内容 | 安全である理由 |
| :---- | :---- | :---- |
| `src/db/migrations.ts:590,614` | `PRAGMA user_version = ${SCHEMA_VERSION}` | 埋め込むのはコード内の数値定数。`PRAGMA` は値をバインドできないため構文上必要 |
| `src/db/repositories/playlistRepo.ts:176-181` | `IN (${placeholders})` | 生成しているのは `?` の並びのみ。**値はすべてバインドしている** |

**継続ルール**

- 新規クエリでも同じ方針を守る。可変長の `IN` 句が必要な場合は、上記と同様に `?` だけを生成し値はバインドする
- SQLite は完全ローカルだが、これは「外部からの攻撃を防ぐ」ためというより、**利用者が入力した記号（`'` や `;` 等）で自分のデータが壊れることを防ぐ**ための対策である点に注意

### S3. 入力検証の二層化（完全性）

| 項目 | 内容 |
| :---- | :---- |
| 目的 | 想定外の値が保存され、集計・成長判定が壊れることを防ぐ |
| 現状 | UI・DB の両層で実施済み |

**内容**

- **第1層（UI）**: `src/lib/validation.ts` が必須・文字数上限・値域・書式を検証し、コンセプト準拠の文言で差し戻す。値域はすべて `src/constants/domain.ts` の定数を参照する（要件定義書記載の値と一致）
- **第2層（DB）**: スキーマの CHECK 制約・NOT NULL・UNIQUE・外部キーが最終的な砦となる。UI をすり抜けた値は保存自体が失敗する
- 境界値（10分ちょうど／721分・4:59と5:00 等）は `src/lib/__tests__/validation.test.ts` で固定し、`npm test` で回帰を検出する

### S4. 通知文面に個人データを含めない（T2）

| 項目 | 内容 |
| :---- | :---- |
| 目的 | ロック画面に表示される通知から、学習内容・ニックネームが第三者に読まれることを防ぐ |
| 現状 | 対策済み |

**内容**

- `src/lib/notification-message.ts` が返す文面は**すべて固定文字列**で、ニックネーム・メモ・学習時間・タグを一切含まない（「もうすぐ夜がひらきます」「この街が目覚めるまで、あと◯分。」等）
- ◯分は通知時刻から計算される固定値であり、利用者の記録に依存しない
- これは世界観（責めない・急かさない）の要請と、覗き見対策が**同じ結論に至った**箇所である

**継続ルール**

- 今後 Phase 7 等で通知を追加する場合も、**文面に利用者の記録を差し込まない**。「今日は◯分学習しました」のような文面はロック画面に生活情報を晒すため採用しない

### S5. ログに個人データを出力しない（T2）

| 項目 | 内容 |
| :---- | :---- |
| 目的 | 開発ログや端末のログバッファにメモ・ニックネームが残ることを防ぐ |
| 現状 | 対策済み（2026-08-01 時点の確認） |

**内容**

- `src/**` に `console.*` は67箇所あるが、**メモ・ニックネーム等の個人データを直接出力している箇所は無い**（確認: `console.*` の引数に `memo` / `nickname` / `title` を含む呼び出しの検索でヒット0）
- 出力はエラー通知と開発時の状態確認に限られる

**継続ルール**

- 利用者の入力値・記録内容をログに出さない
- 任意対応: リリースビルドで `console.*` 自体を落とす（`babel-plugin-transform-remove-console` 等）。現状は個人データを出していないため必須ではないが、混入時の被害を構造的に断てる

### S6. データ消去手段の提供（T1）

| 項目 | 内容 |
| :---- | :---- |
| 目的 | 端末の譲渡・返却時に、利用者が自分の記録を確実に消せるようにする |
| 現状 | 削除処理は実装済み。正式なフロー（確認ダイアログ等）は要件10.10 として設計済み |

**内容**

- `resetUserData()` は `DELETE FROM user` のみを実行し、スキーマの `ON DELETE CASCADE` により学習記録・進捗・設定・マイタグ・計測状態・達成記録が連動削除される
- マスタデータ（街・天気・感情・NPC・環境音・成長閾値・標準タグ）は削除されず、初回起動時と同じ状態に戻る
- **アンインストールでも端末上のデータは消える**（アプリ専有領域のため）。アプリ内の初期化は「端末は手放さずに記録だけ消したい」場合の手段

**確認事項**

- CASCADE の網羅性は、実データを入れた状態で初期化を実行し、**全テーブルの行数が期待どおり0になること**を一度確認する（テーブル追加時にも再確認する）

### S7. 依存関係の最小化と監査（T4）

| 項目 | 内容 |
| :---- | :---- |
| 目的 | 唯一残る外部由来のリスク経路である npm 依存を管理する |
| 現状 | 依存は最小限。監査を実施し、**現時点で利用者端末に影響する脆弱性は無い**と評価した（下記） |

**内容**

- 依存は Expo SDK のパッケージ群と UI 補助（ジェスチャー・アニメーション）に限られ、**状態管理ライブラリ・HTTP クライアント・分析 SDK・広告 SDK を一切導入していない**。Context API 3本構成という設計判断が、結果として依存を減らしている
- パッケージ追加は `npx expo install` を使う（SDK 非互換の回避と、Expo が検証したバージョンに揃えるため）

#### 監査結果（2026-08-01 実施 / `npm audit`）

| 深刻度 | 件数 |
| :---- | ----: |
| critical | 0 |
| high | 42 |
| moderate | 13 |
| **合計** | **55** |

件数は多いが、**これは同一の脆弱性が依存ツリーを伝播して重複計上されたもの**で、根本原因となる勧告（advisory）は次の6件のみである。

| パッケージ | 深刻度 | 内容 | 経路 | 実行タイミング |
| :---- | :---- | :---- | :---- | :---- |
| `brace-expansion` | high | 展開長が非有界で OOM クラッシュ（DoS） | `minimatch` → eslint / jest / glob / `@expo/cli` / RN codegen | 開発・ビルド時 |
| `postcss` | high | sourceMappingURL 経由のパストラバーサルによる任意 `.map` ファイル読み出し（2件） | `@expo/metro-config` | バンドル時 |
| `postcss` | moderate | CSS 文字列化時の未エスケープ `</style>` による XSS | `@expo/metro-config` | バンドル時 |
| `tar` | moderate | 長いパスを含む tar による再帰でスタックオーバーフロー（DoS） | パッケージ展開 | インストール時 |
| `uuid` | moderate | v3/v5/v6 で `buf` 指定時の境界チェック欠落 | `xcode` → `@expo/config-plugins` | iOS ビルド時 |

**評価: 利用者の端末に対するリスクは無い。** 理由は次のとおり。

- 該当パッケージは**すべて開発ツールチェーン（Lint・テスト・バンドラ・CLI・ネイティブ生成）に属し、アプリのバンドルには含まれない**。Metro はエントリポイントから `import` されたモジュールのみをバンドルするため、これらのコードが利用者の端末で実行されることはない
- 脆弱性の性質も、いずれも**攻撃者が細工した入力（tar・CSS・glob パターン）を開発者のマシンで処理させる**ことを前提とする。本アプリのビルド入力はすべて自リポジトリ内のファイルであり、外部から与えられない
- `expo` は直接依存だが、high と判定されているのは `@expo/cli` 等のビルド専用サブパッケージ経由であり、実行時モジュールの問題ではない

**修正を適用しない判断**

- `npm audit fix` が提示する修正はすべて **semver-major**（`expo@54 → 57`、`jest` のメジャー変更）であり、SDK 移行に伴う破壊的変更のリスクのほうが、上記の開発時脆弱性より明らかに大きい
- Expo は SDK 単位でバージョン群を検証しているため、**個別パッケージの上書きは SDK の整合性を壊す**（CLAUDE.md の「パッケージ追加は `npx expo install` を使う」と同じ理由）
- したがって**据え置きとし、リリース前に再度 `npm audit` を実行して評価をやり直す**。critical が出た場合、または実行時に含まれるパッケージ（`react-native` 本体・`expo-*` の実行時モジュール・`react-native-*`）に直接の勧告が出た場合は、この判断を見直す

#### SDK 整合の確認（`npx expo install --check`）

| パッケージ | 現在 | 期待 | 対応 |
| :---- | :---- | :---- | :---- |
| `expo` | 54.0.35 | ~54.0.36 | パッチ差分。**追随する**（`npx expo install expo`） |
| `typescript` | 6.0.3 | ~5.9.2 | Expo 54 の検証範囲より先行している。型チェックが通っている間は据え置き、`npx tsc --noEmit` が壊れた場合に見直す |
| `@types/react` | 19.2.17 | ~19.1.10 | 型定義のみ。同上 |

いずれも**開発時のみに影響し、実行時の安全性には関係しない**。

#### 未使用依存の棚卸し

- `src/components/external-link.tsx` は Expo テンプレート由来で**どこからも参照されていない**。同ファイルと、それが唯一の利用箇所である `expo-web-browser` は削除候補（`expo-linking` は `expo-router` の依存のため残す）
- 使わない依存を減らすことは、そのまま監査対象と攻撃面の縮小になる

| :---- | :---- |

### S9. 外部起点の入力を信用しない（将来対応）

| 項目 | 内容 |
| :---- | :---- |
| 目的 | 他アプリ・外部リンクを経由した入力が、そのままデータ層に届くことを防ぐ |

- `src/components/external-link.tsx` は外部 URL をアプリ内ブラウザで開くが、**どこからも参照されていない**（S7 の削除候補）

**将来ルール**

- deep link でパラメータを受け取る実装を追加する場合、受け取った値は**利用者入力と同等に扱い**、`validation.ts` を通してから DB に渡す
- 外部 URL を開く機能を実装する場合（クレジット画面のリンク等）、**開く先はコード内の定数に限定**し、DB や外部から与えられた URL は開かない

### S10. 写真は端末内に閉じ、位置情報を持たせず、いつでも消せるようにする（T5・T1・T2）

| 項目 | 内容 |
| :---- | :---- |
| 目的 | 「夜の写真」（要件2.6）が、撮った本人の意図を超えて残り続けたり、位置情報を伴って外へ出たりすることを防ぐ |
| 現状 | 要件・スキーマは確定済み。実装はこれから（状態 ⬜） |

**内容**

- **撮影は端末のカメラのみ**とし、写真ライブラリへのアクセス権限は要求しない。読み取る対象を持たないため、既存の写真が本アプリに読まれることはない
- 保存前に**画像を再エンコードして EXIF を除去する**（長辺1280px・JPEG品質0.7程度）。**主目的は撮影位置（GPS）・端末情報の除去**であり、容量削減は副次的な効果である。元ファイルはそのまま保存しない
- 保存先は**アプリ専有領域**（他アプリから読めない）。共有・書き出し・外部送信の機能は設けない
- **削除手段を必ず用意する**。追加・撮り直しは学習日の5:00までに制限するが、**削除だけは過去の夜も含めて常に可能**とする（要件4.1）。写真は室内や人物が写り得るため、記録の一貫性を理由に削除を封じてはならない
- 削除・データ初期化では、**DBの列を消すだけでなく画像ファイルの実体も削除する**。実体はDBの外にあり `ON DELETE CASCADE` の対象外である（要件10.10）
- **カメラ権限は、利用者が撮影を選んだ時点で初めて要求する。** 撮影しなければ権限は要求されず、写真も一切保存されない。この資産を持ちたくない利用者は、撮影を選ばないだけで機能と無縁でいられる
  - 当初は設定「夜の写真」（10.14）でOFFにできる設計だったが、**要件 改訂51で廃止**した。OFFにしてもしなくても撮らない利用者に起きることは同じ（差は選択欄に写真の枠が見えるかどうかだけ）で、設定が実際に防ぐものが無かったためである。設定に頼らず、権限を撮影時にしか要求しない仕組みそのもので保証する
- `app.json` のカメラ権限説明文（iOS `NSCameraUsageDescription`）には、**用途を具体的に書く**（「今夜の空を1枚だけ記録するために使います」等）。「アプリの機能のため」のような説明は、利用者が判断できないため用いない

**将来ルール**

- 写真の書き出し・共有機能を追加する場合は、**EXIF除去が保存時に済んでいることを前提にせず、書き出し時にも確認する**
- 通知・ウィジェット等、アプリ外に表示される面へ写真を出さない（S4「通知文面に個人データを含めない」と同じ理由）

## 5. 対象外とした一般的な対策

以下はモバイルアプリ一般では推奨されるが、本アプリの構成では**脅威が成立しない、または費用対効果が見合わない**ため実施しない。

| 一般的な対策 | 対象外とした理由 |
| :---- | :---- |
| HTTPS / TLS・証明書ピンニング | 外部通信を行わないため保護すべき通信路が存在しない |
| 認証・パスワード保管（ハッシュ化等） | アカウント機能を持たず、認証情報を一切保持しない |
| XSS・CSRF 対策 | WebView も Web フォーム送信も持たない |
| サーバー側のレート制限・入力サニタイズ | サーバーが存在しない |
| DB 暗号化（SQLCipher 等） | OS のサンドボックスを超える攻撃者（root 化端末）を想定しないため（2.3）。導入すると鍵管理という新たな問題が発生し、個人の学習記録に対して見合わない |
| アプリ起動時のパスコード・生体認証ロック | 端末自体のロックに委ねる。世界観（静かに帰ってこられる場所）を損なう副作用が大きい。**利用者から要望があれば再検討する** |
| スクリーンショットの禁止 | 同上。街の見た目を共有したくなる設計であり、機能と衝突する |
| 難読化・改ざん検知 | 保護すべき営利上の資産（課金・独自アルゴリズム）が無い |
| プライバシーポリシー・同意取得 | データを端末外へ一切送信しないため、収集・第三者提供が発生しない。**ストア配布する場合は各ストアの要件に従って別途用意する** |
