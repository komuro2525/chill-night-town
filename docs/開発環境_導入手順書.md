# Chill Night Town 開発環境 導入手順書

チームメンバー全員が同じ開発環境を揃えるための手順書。上から順に進めれば、Expoアプリを実機（またはエミュレータ）で起動し、SQLiteのスキーマを検証できる状態になる。所要時間の目安は初回で60〜90分（ダウンロード時間を除く）。

各ステップの最後に**✅ 確認**を置いているので、必ずクリアしてから次へ進むこと。

---

## 0. 前提となる知識・注意

- 開発OSは**Windows**を前提とする
- ターミナルは**PowerShell**を使う
- 本アプリはiOSメイン対応だが、**開発・動作確認はExpo Goアプリを使えばWindowsから可能**（自分のiPhone/Androidで動かせる）

### 現在のバージョン構成（2026-09-07 時点）

| 項目             | バージョン                                                       |
| ---------------- | ---------------------------------------------------------------- |
| Expo SDK         | **57**                                                           |
| React Native     | 0.86                                                             |
| React            | 19.2                                                             |
| TypeScript       | 6.0                                                              |
| Node.js          | LTS（**20.19.4 / 22.13.0 / 24.3.0 以上**。それ未満だと動かない） |

スマホのExpo Goは**SDK 57対応版**が必要。Expo Goは常に最新SDK 1つだけをサポートするため、ストアの最新版を入れれば揃う。

> **重要**: SDK 57以降、Expo Goでプロジェクトを開くには**パソコン側とスマホ側の両方でExpoアカウントにログインしている必要がある**（1.5参照）。ここでつまずく人が多い。

## 1. 基本ツールのインストール

### 1.1 Visual Studio Code

公式サイト（https://code.visualstudio.com/）からインストール。インストール済みの人はスキップ。

### 1.2 Node.js（LTS版）

Expo / React Nativeの実行に必須。**LTS版（長期サポート版）**を入れること。

公式サイト（https://nodejs.org/）からLTS版のインストーラをダウンロードして実行する

> **注意**: インストーラをダウンロードしただけでは終わらない。ダウンロードしたファイル（`.msi`）を**ダブルクリックして開き、ウィザードを最後まで進めて完了させる**こと。また、インストール完了後にPATHが反映されるのは**新しく開いたPowerShellのみ**。すでに開いているPowerShellでは反映されないので、一度閉じて開き直してから確認すること。

**✅ 確認**（ターミナルで実行）:

```bash
node -v    # v22.x.x など LTS のバージョンが表示されればOK
npm -v     # 10.x 以上ならOK（Node 22 LTSにはnpm 10が同梱される）
```

> **`npm -v` で「このシステムではスクリプトの実行が無効になっているため...」というエラーが出た場合**: PowerShellの既定のセキュリティ設定でスクリプト実行がブロックされているのが原因（Node固有の問題ではない）。以下を実行して自分のアカウント用に許可すれば直る。
>
> ```powershell
> Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
> ```
>
> 確認を聞かれたら `Y` を入力。管理者権限は不要。

### 1.3 Git

https://git-scm.com/ からインストール（設定はすべてデフォルトでOK）

**✅ 確認**:

```bash
git --version
```

初回のみ、自分の名前とメールを設定する:

```bash
git config --global user.name "自分の名前"
git config --global user.email "自分のメールアドレス"
```

> **注意**: この設定を忘れたまま `git commit` はできてしまう（ローカルで完結する操作のため）。後から「メールアドレスは設定したのにGitHubアカウントが見つからない」と混乱しがちなので注意。`git config --global user.email` で何も表示されない場合は未設定なので、上記コマンドで設定しておくこと。GitHubアカウント自体をまだ作っていない場合は https://github.com/signup から作成する。

### 1.4 SQLite CLI（スキーマ検証用）

アプリに入れる前に、スキーマSQLやシードSQLを手元で検証するために使う。

次のいずれかで導入する:

- `winget install SQLite.SQLite`（PowerShellで実行。推奨）
- または https://www.sqlite.org/download.html の「sqlite-tools」zipを展開し、`sqlite3.exe` のあるフォルダにPATHを通す

> **注意**: `winget install SQLite.SQLite` を実行すると、先に `msstore` ソースの利用規約への同意を求められることがある（`Y`で進めてよい）。それでも `No package found matching input criteria.` と出て失敗する場合は、検索対象ソースを明示して再実行する。
>
> ```powershell
> winget install --id SQLite.SQLite --source winget
> ```
>
> インストール後はここでも**新しいPowerShellを開き直してから**確認すること。

**✅ 確認**:

```bash
sqlite3 --version
```

### 1.5 Expo Go（スマホ側アプリ）

自分のスマホにストアから **Expo Go** をインストールする（iOS: App Store / Android: Google Play）。開発中のアプリを実機で動かすためのビューアで、これがあればiPhoneでもAndroidでも動作確認できる。**常に最新版にアップデートしておくこと**（古いままだと後述のSDKバージョン不一致の原因になる）。

#### Expoアカウントの作成とログイン（SDK 57以降は必須）

**Expo Go でプロジェクトを開くには、パソコン側（Expo CLI）とスマホ側（Expo Go）の両方が、同じExpoアカウントでログインしている必要がある。** 未ログインだと、QRを読んでも次の画面が出て起動できない。

```
There was a problem running the requested project.
You need to be signed in to Expo Go and Expo CLI to open your project.
Run "npx expo login" on your computer to sign in with Expo CLI.
```

Expo側が導入した仕様であり、設定ミスではない。**現時点ではiOS版のExpo Goにのみ適用**されている（Android版も今後適用予定）。

**手順:**

1. アカウントを持っていなければ作る（PowerShellで実行。ブラウザが開く）

   ```powershell
   npx expo register
   ```

2. パソコン側でログインする

   ```powershell
   npx expo login
   ```

3. スマホのExpo Goでもログインする
   Expo Goのホーム画面 → **右上のアバターアイコン** → 同じアカウントでログイン

**✅ 確認**:

```powershell
npx expo whoami    # 自分のユーザー名が表示されればOK（Not logged in ならログインできていない）
```

## 3. Claude Code（AIコーディング支援）の導入【推奨・任意】

Claude Codeは、Anthropicのエージェント型コーディングツール。リポジトリ全体を読んでコードの作成・修正・デバッグを行い、変更は差分（diff）として提示されるので、承認してから反映できる。本プロジェクトでは設計ドキュメント一式が揃っているため、それを読ませて実装補助に使うと効果が大きい。

> **前提（重要）**: Claude Codeの利用には**有料プラン（Pro以上）のAnthropicアカウント**またはAPIキーが必要で、無料プランでは使えない。そのため本節は**任意**とする。使わないメンバーは「4. Expoプロジェクトの作成」へ進んでよい。役割分担として「設計相談はClaude（チャット）、コードの実作業はClaude Code」という使い分けになる。

### 3.1 VS Code拡張のインストール（推奨ルート）

1. VS Codeの拡張機能ビュー（`Ctrl+Shift+X`）で「**Claude Code**」を検索
2. **発行元が Anthropic** のものをインストール（似た名前のコミュニティ製と間違えないこと）
3. プロジェクトのファイルを開くと、エディタ右上に**Sparkアイコン（✱）**が表示される。表示されない場合はコマンドパレット（`Ctrl+Shift+P`）から「Developer: Reload Window」を実行
4. アイコンをクリックして初回起動すると、ブラウザでAnthropicアカウントのサインインを求められるので完了する

拡張機能にはCLI本体が同梱されているため、別途のインストールは基本的に不要。

**✅ 確認**: Claudeのパネルで適当なファイルを開いた状態で「このファイルの内容を説明して」と送り、応答が返ればOK。コード変更を指示した場合はdiff（差分）が表示され、Accept/Rejectで反映を制御できる。

> **セッションの開始方法（初めての人向け）**: ①VS Codeでプロジェクトフォルダを開く → ②何かファイルを1つ開いた状態にする（フォルダだけでなくファイルを開いている必要がある）→ ③エディタ右上の✱（Sparkアイコン）をクリック → ④初回はブラウザでサインインを求められるので完了する → ⑤チャット欄に何か送って応答が返れば成功。

> **「Webビューの読み込みエラー: Could not register service worker...」が出る場合**: これはClaude Code拡張に限らず、SQLite ViewerなどVS Codeの他のWebview系拡張でも起こりうる、VS Code自体のWebviewキャッシュ不具合。以下の順に試すと直ることが多い。
>
> 1. VS Codeを完全に終了して再起動する
> 2. それでも直らなければPCを再起動する
> 3. Help（ヘルプ）メニュー →「Check for Updates」でVS Code自体を最新化する
> 4. それでも直らない場合、VS Codeを閉じた状態で以下を実行してキャッシュを削除する（データは自動生成されるものなので削除して問題ない）
>    ```powershell
>    Remove-Item -Recurse -Force "$env:APPDATA\Code\Service Worker" -ErrorAction SilentlyContinue
>    Remove-Item -Recurse -Force "$env:APPDATA\Code\Cache" -ErrorAction SilentlyContinue
>    Remove-Item -Recurse -Force "$env:APPDATA\Code\CachedData" -ErrorAction SilentlyContinue
>    ```

### 3.2 ターミナル（CLI）で使いたい場合

コマンドラインで使う場合は、CLIを別途インストールする:

```bash
npm install -g @anthropic-ai/claude-code
claude --version    # バージョンが表示されればOK
```

プロジェクトフォルダで `claude` を実行するとセッションが始まる（初回はサインインあり）。CLIの利用にはGit for Windowsが必要だが、手順1.3で導入済みなので追加作業は不要。

> **補足**: 3.1（VS Code拡張）と3.2（CLI）は**両方入れても問題ない**。拡張機能にCLI本体が同梱されているので3.1だけでも十分だが、エディタを開かずターミナル単体で使いたい場合は3.2も追加しておくと便利。

### 3.3 CLAUDE.md の作成（チームで1回・コミットする）

リポジトリ直下に `CLAUDE.md` を置くと、Claude Codeはセッション開始時に必ずこれを読む。**プロジェクトの前提をここに書いておけば、毎回説明し直す必要がなくなり、チーム全員のClaudeが同じ前提で動く。** Claude Codeのプロンプトで `/init` を実行すると、コードベースを解析して雛形を自動生成してくれる。

本プロジェクトでは最低限、以下を書いておくとよい:

- 技術スタック（Expo / Expo Router / TypeScript / SQLite、状態管理はContext API 3本構成）
- 設計ドキュメントの場所（要件定義書v2・ユースケース設計書v2・テーブル定義書v2・スキーマ・シードのパス）と「実装judgmentに迷ったらこれらを参照する」旨
- 重要な用語定義（**学習日＝18:00〜翌5:00サイクル**、実績学習時間＝一時停止・休憩フェーズを除く、など0章の内容）
- コーディング規約（Prettier準拠、コメントは日本語可、など）

> **推奨構成**: 設計ドキュメントの本文をCLAUDE.mdに全部書き込むのではなく、`docs/` フォルダに個別ファイルとして分けて置き、CLAUDE.mdには**そのパス一覧と参照ルール**だけを書く（索引のような役割）。理由は、CLAUDE.mdはセッション開始時に毎回読み込まれるため巨大化を避けたいことと、設計書は個別に更新されるため差分管理がしやすいこと。
>
> ```
> chill-night-town/
> ├─ CLAUDE.md
> └─ docs/
>    ├─ 要件定義書_v2.md
>    ├─ ユースケース設計書_v2.md
>    ├─ テーブル定義書_v2.md
>    ├─ chill_night_town_スキーマ_v2.sql
>    └─ chill_night_town_シードデータ.sql
> ```
>
> 注意点: `db/` フォルダには**実行可能なSQLファイルだけ**を置き、テーブル定義書やER図などの設計資料は `docs/` フォルダに置くこと。役割（実行用 / 参照用）を分けておくと管理しやすい。

`CLAUDE.md` は**Gitにコミットして共有する**こと。

### 3.4 使い方の最初のルール

- 権限モードは最初は**Normal（変更のたびに確認）**のままにする。慣れるまでAuto-acceptにしない
- `@ファイル名` でファイルを参照できる（例: `@db/chill_night_town_スキーマ_v2.sql を読んでDB接続層を作って`）
- 大きめの変更は**Planモード**を使い、実装計画を確認してから着手させる
- **Claudeが書いたコードも必ず自分でレビューしてからコミットする**。理解できないコードをそのままマージしない（卒業研究として説明責任があるため）

詳細は公式ドキュメント参照: https://docs.claude.com/en/docs/claude-code/overview

## 4. Expoプロジェクトの作成

> **リポジトリ担当者が1回だけ実施**する。他のメンバーは「6. 既存リポジトリからの参加」へ。
> 以降のコマンド例はすべてPowerShell（Windows）で実行する前提。

### 4.0 プロジェクトフォルダの置き場所

`C:` 直下などに開発用フォルダを作ってその中で作業すること（例: `C:\dev`）。

```powershell
mkdir C:\dev
cd C:\dev
```

**デスクトップやドキュメントは避ける**こと。Windowsの既定設定でOneDriveと同期対象になっていることが多く、`node_modules`（ファイル数が数万個）が同期されるとPCが重くなったり、同期エラー・ファイルロックで正常に動かないことがある。またパスに日本語やスペースが含まれる場所も、一部ツールでビルドエラーの原因になるため避ける。

### 4.1 プロジェクト作成

作業用フォルダで以下を実行:

```bash
npx create-expo-app@latest chill-night-town
cd chill-night-town
```

最新のデフォルトテンプレートには **TypeScript と Expo Router が最初から含まれている**。作成後、`app/` フォルダ（または `src/app/` フォルダ）と `tsconfig.json` が存在することを確認する。

> **注意（src構成の場合）**: 作成時の選択によっては `app/` が `src/app/` の中に入る構成になることがある（起動時のログに `Using src/app as the root directory for Expo Router.` と出ていればこの構成）。この場合、後述の `contexts/` や `components/` など `@/` エイリアスで参照するフォルダは**すべて `src/` の中**に作る必要がある。プロジェクト作成直後に `src` フォルダの有無を確認しておくこと。

### 4.1.5 SDKバージョンとExpo Goの対応確認（重要）

`npx create-expo-app@latest` は**その時点の最新SDK**でプロジェクトを作る。しかし、スマホ側のExpo Goアプリ（ストア版）がそのSDKにまだ対応していないことがあり、その場合QRを読んでも次のエラーになる。

```
ERROR  Project is incompatible with this version of Expo Go
The project you requested requires a newer version of Expo Go.
```

**対処手順:**

1. スマホでExpo Goを最新版にアップデートする（それでも直らないことがある）
2. Expo Goアプリを開き、**「Supported SDK」欄に表示されているバージョン**を確認する
3. プロジェクト側のSDKをそのバージョンに合わせる。**この作業は、パッケージを何も追加していない、作ったばかりのまっさらな状態で行うこと**（後から下げようとすると依存関係の衝突が起きやすいため）。
   ```powershell
   npx expo install expo@^57.0.0    # ここは確認したSupported SDKの番号に置き換える
   npx expo install --fix
   ```
4. `npm error ERESOLVE could not resolve` のような依存関係の衝突が出た場合は、一度クリーンにしてから入れ直す。
   ```powershell
   Remove-Item -Recurse -Force node_modules
   Remove-Item package-lock.json
   npm install --legacy-peer-deps
   ```
5. 起動して確認する。
   ```powershell
   npx expo start -c
   ```

> **補足**: 新しいSDK向けのデフォルトテンプレートには、そのSDKだけの実験的機能（例: `expo-router/unstable-native-tabs` の `NativeTabs`、`expo-router` からの `ThemeProvider` 直接importなど）が使われていることがある。SDKを下げた後に
>
> ```
> Render Error
> Element type is invalid: expected a string ... but got: undefined.
> Check the render method of `TabLayout(./_layout.tsx)`.
> ```
>
> のようなエラーが出た場合、テンプレートのコードが新SDK専用の機能をそのまま参照していないか確認する。該当箇所は標準の機能に書き換える。
>
> - `components/app-tabs.tsx` などで `NativeTabs`（`expo-router/unstable-native-tabs`）を使っている → 標準の `Tabs`（`expo-router`）に書き換える
> - `app/_layout.tsx` などで `ThemeProvider` / `DarkTheme` / `DefaultTheme` を `expo-router` からimportしている → SDK 55以前へ下げた場合のみ `@react-navigation/native` からimportするよう変更する

> **重要（SDK 56以降）**: 上の最後の項目は**SDK 56で逆転した**。SDK 56から `expo-router` は `@react-navigation/*` に依存しなくなり、`@react-navigation/native` は自動では入らない。
>
> **本プロジェクト（SDK 57）では `expo-router` から import するのが正しい。** `useIsFocused` / `ThemeProvider` / `DarkTheme` / `DefaultTheme` はいずれも `expo-router` が再エクスポートしている。
>
> ```ts
> // SDK 56以降（本プロジェクト）
> import { DarkTheme, DefaultTheme, Stack, ThemeProvider, useIsFocused, useRouter } from "expo-router";
>
> // SDK 55以前
> import { DarkTheme, DefaultTheme, ThemeProvider, useIsFocused } from "@react-navigation/native";
> ```
>
> `Cannot find module '@react-navigation/native'` が出たら、この移行を忘れている。

### 4.2 必要パッケージの追加

本アプリで使用が確定しているExpoパッケージを入れる。**必ず `npx expo install` を使う**こと（npm installだとSDKと互換性のないバージョンが入ることがある）。

```bash
npx expo install expo-sqlite expo-notifications expo-audio expo-battery expo-keep-awake expo-screen-orientation
```

各パッケージの用途:

| パッケージ              | 用途（対応する仕様）                                      |
| ----------------------- | --------------------------------------------------------- |
| expo-sqlite             | ローカルDB（全データ保存）                                |
| expo-notifications      | 学習開始予定のローカル通知（12章）                        |
| expo-audio              | BGM・環境音・効果音・鐘の再生（9章）                      |
| expo-battery            | 横画面のバッテリー残量表示（2.4）                         |
| expo-keep-awake         | タイマー稼働中・横画面・鑑賞モード中のスリープ防止（3.2） |
| expo-screen-orientation | ホーム画面のみ横向き許可、他画面は縦固定（2.4）           |

> **注意①（音声）**: 音声はSDKのバージョンによって `expo-audio`（新）と `expo-av`（旧・非推奨）が分かれる。上のコマンドでexpo-audioが入らない古いSDKだった場合のみexpo-avを使う。導入時にExpo公式ドキュメントで現行の推奨を確認すること。

> **注意②（通知）**: SDK 53以降、Expo Goでは**プッシュ通知（リモート通知）が利用できない**が、**ローカル通知は引き続き利用できる**（公式ドキュメント明記）。本アプリの通知は学習開始リマインダーのローカル通知のみなので、**Expo Goでの開発に支障はない**。開発中に「push notifications are not supported in Expo Go」系の警告が表示されても、リモート通知に関するものなので無視してよい。

> **注意③（npm audit警告）**: `npx expo install` の実行後に `X moderate severity vulnerabilities` のような警告が出ることがあるが、Expo/React Native開発ではほぼ毎回出る定型の警告で、今の段階で対応は不要。**`npm audit fix --force` は実行しないこと**（パッケージが強制的に書き換えられ、Expoとの互換性が壊れることがある）。

**✅ 確認**:

```bash
npx expo start
```

QRコードが表示されたら、スマホのExpo Go（Androidはアプリ内、iOSは標準カメラ）でスキャン → テンプレート画面がスマホに表示されればOK。**PCとスマホが同じWi-Fiに接続されている必要がある**。表示されない場合は `npx expo start --tunnel` を試す。

> **`--tunnel` を使う場合の注意**:
>
> - 初回は `@expo/ngrok` の追加インストールを聞かれるので `y` で進める。インストール後、`CommandError: Install @expo/ngrok and try again` と出る場合はPATH反映のため**新しいPowerShellを開き直してから**再実行する。それでも直らない場合はプロジェクトのローカル依存として入れ直す（`npm install @expo/ngrok --save-dev`）。
> - `ngrok tunnel took too long to connect` と出る場合、PCとスマホを同一のモバイル端末のテザリング（インターネット共有）で繋いでいると、自己ループ通信になり不安定になりやすい。可能なら別のWi-Fi（自宅ルーター等）で試す。
> - Windowsファイアウォールの警告ポップアップが出た場合は「アクセスを許可する」を選ぶ。

## 5. Context APIの骨組みを作る（初回セットアップ時に1回）

> **リポジトリ担当者が実施**する。他のメンバーは「6. 既存リポジトリからの参加」へ。

### 5.1 なぜContext APIを使うのか

当初は「Context APIは使わない」方針だったが、その後の仕様追加により**アプリ全体で共有される状態**が増えたため、Context APIを採用する方針に変更した。共有が必要なのは以下の3種類。

- **タイマー状態**：ホーム／タイマー表示／横画面／設定ロック判定など全画面で参照される
- **オーディオ状態**：BGMは画面をまたいで再生を継続し、ミニプレイヤー・おやすみ機能・ダッキング処理から参照される
- **ユーザー設定**：目標時間・成長方式などの変更が、各画面へ即座に反映される必要がある

Context APIはReactの標準機能であり、**追加パッケージのインストールは不要**。「Providerで包む」「useContextで読む」の2つを覚えるだけで使える。

### 5.2 3つのContextを作る

以下のディレクトリ構成でファイルを作る（`contexts/` フォルダをプロジェクト直下に新規作成）。中身は当面は空のスタブでよく、実装は各機能を作るときに埋めていく。

```
chill-night-town/
├─ contexts/
│   ├─ TimerContext.tsx
│   ├─ AudioContext.tsx
│   └─ SettingsContext.tsx
└─ app/
    └─ _layout.tsx    ← ここで3つのProviderを重ねる
```

> **`src/app` 構成の場合**: 4.1の注意にある通り、プロジェクトが `src/app/` 構成（`@/` エイリアスが `src/` を指す構成）なら、`contexts/` は必ず `src/` の中に作ること（`src/contexts/`）。そうしないと `@/contexts/TimerContext` のようなエイリアスimportが解決できずエラーになる。

**TimerContext.tsx**（雛形）:

```tsx
import { createContext, useContext, useState, ReactNode } from "react";

type TimerState = {
  isRunning: boolean;
  // 後で: 経過時間、モード、フェーズ、一時停止時刻など
};

type TimerContextValue = {
  state: TimerState;
  // 後で: start, pause, resume, finish などのメソッド
};

const TimerContext = createContext<TimerContextValue | null>(null);

export function TimerProvider({ children }: { children: ReactNode }) {
  // setStateは実装時に使用する。雛形段階ではlint警告を避けるため受け取らない
  const [state] = useState<TimerState>({ isRunning: false });
  return (
    <TimerContext.Provider value={{ state }}>{children}</TimerContext.Provider>
  );
}

export function useTimer() {
  const ctx = useContext(TimerContext);
  if (!ctx) throw new Error("useTimer は TimerProvider の内側で使うこと");
  return ctx;
}
```

**AudioContext.tsx** と **SettingsContext.tsx** も同じパターンで作る（型名とファイル名を差し替えるだけ）。例えば `AudioContext.tsx` なら `TimerState`→`AudioState`、`TimerProvider`→`AudioProvider`、`useTimer`→`useAudio` のように名前を丸ごと置き換える（コピーしてリネームしただけの中身にならないよう注意）。

### 5.3 Providerで全画面を包む

Expo Routerでは `app/_layout.tsx`（`src/app/_layout.tsx`）がアプリ全体のレイアウトになる。ここで3つのProviderを入れ子にする。

```tsx
import { Stack } from "expo-router";
import { TimerProvider } from "../contexts/TimerContext";
import { AudioProvider } from "../contexts/AudioContext";
import { SettingsProvider } from "../contexts/SettingsContext";

export default function RootLayout() {
  return (
    <SettingsProvider>
      <AudioProvider>
        <TimerProvider>
          <Stack />
        </TimerProvider>
      </AudioProvider>
    </SettingsProvider>
  );
}
```

順番のポイント：**外側ほど「他のContextに依存しない」もの**を置く。設定は他のContextから読まれる側なので一番外、タイマーは設定を参照するので内側、という配置。

> **タブ構成テンプレートの場合**: テンプレートによっては `_layout.tsx` の中身が `<Stack />` ではなく、独自の `AppTabs` コンポーネントなどタブ構成になっていることがある。その場合も考え方は同じで、既存の中身（`ThemeProvider`や`AppTabs`など）の外側に3つのProviderを追加すればよい。例:
>
> ```tsx
> import {
>   DarkTheme,
>   DefaultTheme,
>   ThemeProvider,
> } from "@react-navigation/native";
> import { SettingsProvider } from "@/contexts/SettingsContext";
> import { AudioProvider } from "@/contexts/AudioContext";
> import { TimerProvider } from "@/contexts/TimerContext";
> import AppTabs from "@/components/app-tabs";
>
> export default function TabLayout() {
>   return (
>     <ThemeProvider value={DefaultTheme}>
>       <SettingsProvider>
>         <AudioProvider>
>           <TimerProvider>
>             <AppTabs />
>           </TimerProvider>
>         </AudioProvider>
>       </SettingsProvider>
>     </ThemeProvider>
>   );
> }
> ```

### 5.4 使い方（例：画面から状態を読む）

```tsx
import { useTimer } from "../contexts/TimerContext";

export default function HomeScreen() {
  const { state } = useTimer();
  return <Text>{state.isRunning ? "学習中" : "待機中"}</Text>;
}
```

**✅ 確認**: `npx expo start` を実行し、Expo Goでアプリが起動時にエラーを出さずに表示されればOK。中身が空でも、Providerの階層が正しく組めていれば動く。

### 5.5 注意点

- **1つの巨大Contextに何でも詰め込まない**。役割で3つに分けているのは、不要な再描画（Context値の変化で購読側が全部更新される問題）を避けるため
- **Provider外でuseXxxを呼ばない**。上のTimerProviderの例のように、Provider外での使用はエラーになるガードを入れておくとバグに気づきやすい
- 実装が進むと `useEffect` や `useReducer` を組み合わせることになるが、その段階は各機能実装時に個別に検討する

## 7. SQLiteスキーマの検証（実機に入れる前のチェック方法）

アプリに組み込む前に、SQLの変更はまず手元のCLIで検証する習慣をつける。

> **注意（PowerShell）**: 以下のような `<` を使ったリダイレクトは**PowerShellでは使えない**（bashと異なる仕様のため、`演算子 '<' は、今後の使用のために予約されています` というエラーになる）。PowerShellでは代わりに `cmd /c` 経由か `Get-Content` のパイプを使う。

```bash
cd db
sqlite3 test.db < chill_night_town_スキーマ_v2.sql
sqlite3 test.db < chill_night_town_シードデータ.sql
```

PowerShellでの実行方法（**方法1を推奨**。日本語コメントを含む場合、方法2は文字コードの扱いでエラーになることがある）:

```powershell
# 方法1: cmd経由（推奨）
cmd /c "sqlite3 test.db < chill_night_town_スキーマ_v2.sql"
cmd /c "sqlite3 test.db < chill_night_town_シードデータ.sql"

# 方法2: パイプ
Get-Content chill_night_town_スキーマ_v2.sql | sqlite3 test.db
Get-Content chill_night_town_シードデータ.sql | sqlite3 test.db
```

エラーが出なければ、`test.db` をVS Codeで開く（SQLite Viewer拡張が自動で開いてくれる）。テーブル一覧と、night_weatherに11件・npc_messageに30件などのマスタが入っていることを目視確認できる。

> **SQLite Viewerで開いたときに「Webビューの読み込みエラー: Could not register service worker...」が出る場合**: 拡張機能個別の不具合ではなく、VS Code自体のWebviewキャッシュ不具合であることが多い（3.1の補足を参照）。VS Code再起動・PC再起動・キャッシュ削除で直らない場合は、無理に拡張機能で開かず、下記の対話モードでCLIから直接確認すればよい。

対話モードで確認する場合:

```bash
sqlite3 test.db
sqlite> .tables                          -- テーブル一覧（18個あるはず）
sqlite> SELECT COUNT(*) FROM npc_message; -- 30 が返ればOK
sqlite> .quit
```

> **注意**: `test.db` は検証用の使い捨てファイル。コミットしないこと（.gitignoreに `db/*.db` を追加しておくと安全。追加方法は4.3参照）。

## 8. Gitブランチ運用ルール（最小構成）

- **main**: 常に動く状態を保つ。直接コミットしない

- マージ前に最低1人がざっと目を通す（Pull Request推奨。難しければ口頭確認でも可）
- こまめにコミットし、コミットメッセージは「何をしたか」が分かる日本語でOK

日常的なコミットの流れ:

```powershell
git status               # 何が変わったか確認（任意だけど推奨）
git add .                # 変更を全部ステージに追加
git commit -m "何をしたかが分かる日本語メッセージ"
git push                 # リモート（GitHub等）に反映
```

> **コミット前のチェック**: `git status` の結果に `db/test.db` のような検証用の使い捨てファイルが Untracked として出ていないか必ず確認すること。出ている場合は `.gitignore` に該当パターンが入っていない可能性が高いので、先に4.3の手順で追記してから `git add` する。

機能ブランチを使う場合:

```powershell
git checkout -b feature/timer-core      # 新しいブランチを作って切り替え
# 作業・コミットを繰り返す
```

| PowerShellで `sqlite3 test.db < xxx.sql` を実行すると `演算子 '<' は...予約されています`  | PowerShellは`<`リダイレクトに対応していない。`cmd /c "sqlite3 test.db < xxx.sql"` または `Get-Content xxx.sql \| sqlite3 test.db` を使う（詳細は7章参照）                                                           |
| VS Codeで「Webビューの読み込みエラー: Could not register service worker...」              | 拡張機能個別ではなくVS Code自体のWebviewキャッシュ不具合。VS Code再起動→PC再起動→VS Codeのアップデート→キャッシュフォルダ削除の順で試す（詳細は3.1の補足を参照）                                                    |
| `git status` に検証用の `db/test.db` がUntrackedとして出る                                | `.gitignore` に `db/*.db` が入っていない。4.3の `Add-Content .gitignore` コマンドで追記してから再度 `git status` で消えたことを確認する                                                                             |
