# 導入手順書 作成手引き

提出用の導入手順書を、チームで分担して作るための手引き。**システム構成 → 担当 → やること**の順にまとめる。

インストールの具体的な手順はここには書かない。**`docs/開発環境_導入手順書.md` に全部あるので、それを見ながら進めれば作れる。**

### 使う資料

| #   | 資料                                  | 役割                                                             |
| :-- | :------------------------------------ | :--------------------------------------------------------------- |
| 1   | 本書                                  | 作り方。まずこれを読む                                           |
| 2   | `docs/開発環境_導入手順書.md`         | **中身の元。手順はここから持ってくる**。触らずそのまま残す       |
| 3   | サンプル PDF（PeerWisdom / 別チーム） | 見た目の参考だけ。**中身は真似しない**（構成が違う。→ 1節・3.5） |

---

## 1. システム構成

**手順書を書く前に、何を導入することになるのかを掴んでおくこと。** ここが分かっていないと担当を分けられない。

### 一番の特徴: サーバーが無い

Chill Night Town は**サーバーを持たないスマートフォンアプリ**である。データはすべて端末内の SQLite に入り、外部へ出ない。

このため、一般的な業務システムの手順書にある章が**まるごと存在しない**。

| 普通はある章                               | 本プロジェクト |
| :----------------------------------------- | :------------- |
| サーバー構築（AWS / Windows Server）       | **無い**       |
| アプリケーションサーバー（Tomcat）         | **無い**       |
| データベース製品のインストール（MySQL）    | **無い**       |
| DB ドライバの配置（JDBC）                  | **無い**       |
| 接続情報（ホスト・ポート・ID・パスワード） | **無い**       |

### 導入対象は2つだけ

```
┌─────────────────────────────────────┐ ← 導入する
│ 開発PC（Windows 11 / PowerShell）                            │
│   Node.js + npm … 依存解決・開発サーバー起動                 │
│   Git          … ソース取得                                  │
│   VS Code + 拡張 … 編集                                      │
│   SQLite CLI   … スキーマ検証                                │
└──────────────────┬──────────────────┘
                   │ 同一 Wi-Fi 上で QR を読んで接続
┌──────────────────┴──────────────────┐ ← 導入する
│ スマートフォン（iOS / Android）                              │
│   Expo Go … 開発中のアプリを実機で動かすビューア             │
│     └ アプリ本体                                             │
│         └ SQLite … 端末内に自動生成（導入作業なし）          │
└─────────────────────────────────────┘
```

### バージョン一覧

手順書の「システム条件」に載せる値は、**`docs/開発環境_導入手順書.md` の 0章「詳細なバージョン一覧」にまとめてある。** そこから転記すること。

- 開発PCに入れるツール（Node.js / npm / Git / SQLite CLI）
- アプリの基盤（Expo SDK / React Native / React / TypeScript ほか）
- Expoモジュール 22件・その他のライブラリ 10件

いずれも**実際に入っている版**であり、`package.json` の範囲指定（`^` や `~`）ではない。値を取り直すときは `npm ls --depth=0` を実行する。

**ここに一覧を再掲しないこと。** 二重に持つと、片方だけ更新されてズレる。

### データベースは「導入しない」

SQLite はアプリに組み込まれるライブラリで、製品として入れるものではない。スキーマと初期データはアプリに同梱されており、**初回起動時に自動で作られる**。手作業で SQL を流す工程は無い。

ただし**「無い」で終わらせず、なぜ無いのかを一文書く。** 抜けたのか意図的に外したのかが読む人に分からないと、卒業研究として説明できない。

## 2. 担当

**先に設計書を書いて自分で試す。問題なかったらほかの担当の人に見てもらいながら導入する。**

> **章番号の読み方（重要）**
> 本書には2種類の章番号が出てくる。混同しないこと。
>
> - **「作る〇章」** … これから作る**提出用の導入手順書**の章。章立ては 3.1 の「作る目次」にある
> - **「元の〇章 / 〇.〇」** … 転記元である **`docs/開発環境_導入手順書.md`** の節番号
>
> **「元の」が付いていない章番号は、すべて作る導入手順書のもの**と読んでよい。

| 担当  | 作る章                                          | **元のどこを使うか**（`docs/開発環境_導入手順書.md`）                                                       |
| :---- | :---------------------------------------------- | :---------------------------------------------------------------------------------------------------------- |
| A     | **作る1章** はじめに                            | **元の 0章 まるごと**（前提となる知識・注意／現在のバージョン構成／詳細なバージョン一覧）                    |
| B     | **作る2章** アプリを動かすまで                  | **元の 1.2 Node.js**／**1.3 Git**／**1.5 Expo Go**／**6章 既存リポジトリからの参加**                        |
| C     | **作る3章** 開発を引き継ぐための追加導入        | **元の 1.1 VS Code**／**1.4 SQLite CLI**／**2章 VS Code 拡張機能**／**7章 SQLiteスキーマの検証**／**8章 Gitブランチ運用ルール** |
| **D** | **検証** → 結果を**作る5章・6章**へ             | **元の 9章 セットアップ完了チェックリスト**／**巻末のトラブルシューティング**（導入作業に関係するものだけ） |
| 全員  | **作る4章** データベースについて・付録・通し読み | 本書 1節「データベースは『導入しない』」                                                                    |

> **元の1章は B と C で分かれる。** 1.1（VS Code）と 1.4（SQLite CLI）は C、1.2・1.3・1.5 は B。
> 番号が連続していないので、**自分の番号だけを拾うこと**。まとめて写すと担当外まで入る。

### 使わない章（元の文書にあるが、作る手順書には入れない）

| 使わない部分                                    | 理由                                               |
| :---------------------------------------------- | :------------------------------------------------- |
| **元の 3章 Claude Code の導入**（3.1〜3.4）     | 任意ツール。無くてもアプリは動く                   |
| **元の 4章 Expoプロジェクトの作成**（4.0〜4.3） | プロジェクトを**作った時の記録**。導入手順ではない |
| **元の 5章 Context APIの骨組み**（5.1〜5.5）    | 設計の話であって導入ではない                       |
| 巻末トラブルのうち SDK ダウングレード関連       | 今の構成（SDK 57 固定）では起きない                |

### 見てもらうときのルール

**書いた人は口を出さない。** 見ている人が詰まったら、**その時点で手順書の欠陥**である。口で補わずに手順書を直す。

**D は2回やる。**

1. **作る2章だけを読んでアプリが起動するか**
2. **作る2章＋3章で開発できる状態になるか**

1 の途中で作る3章の内容が必要になったら、その項目は作る2章へ移す。

## 3. やること

### 3.1. 手順書の章立て

読む人の目的が2種類あるので、**手順を2つのルートに分ける**。

|                    | **ルート A**               | **ルート B**                     |
| :----------------- | :------------------------- | :------------------------------- |
| 読む人             | 審査員・動作を見たい人     | 開発を引き継ぐ人                 |
| やりたいこと       | 実機で動かして確認するだけ | 編集・テスト・スキーマ検証もする |
| ソースを編集するか | しない                     | する                             |
| 読む章             | **2章** → 5章              | **2章 ＋ 3章** → 5章             |
| 所要時間           | 約30分                     | 約60〜90分                       |

**B は A に足す形。** 3章には「2章に加えて要るもの」だけを書く。

```
ルート A ─→ 2章 ─→ 5章 動作確認 ─→ 完了
                │
ルート B ─→ 2章 ┴→ 3章 ─→ 5章 ─→ 完了
```

**作る目次は次のとおり。** 本書で「作る1章」「作る2章」と呼んでいるのはこれを指す。

```
1. はじめに
   1.1 手順書概要（サーバーが無いこと）
   1.2 読む章の選び方（ルート A / B）
   1.3 システム構成（図）
   1.4 システム条件（PC・スマホ・ネットワーク／ソフトのバージョン表）
2. 【A / B 共通】アプリを動かすまで
   Node.js / Git / Expo Go / Expo アカウント / clone・npm ci / npm start
3. 【B のみ】開発を引き継ぐための追加導入
   VS Code / 拡張機能 / SQLite CLI / tsc・lint・test / ブランチ運用 /
   引き継いだら最初に読むもの / 本書で扱わないもの（開発ビルド）
4. データベースについて（導入作業が不要な理由）
5. 動作確認（PC 側・端末側のチェックリスト）
6. トラブルシューティング
付録 関連ドキュメント
```

### 3.2. どちらの章に書くかの判断

**それが無いとアプリが起動しないなら2章。編集や検証ができないだけなら3章。**

| 章                        | 入るもの                                                                                              | 理由                     |
| :------------------------ | :---------------------------------------------------------------------------------------------------- | :----------------------- |
| **作る2章（A / B 共通）** | Node.js / Git / Expo Go / Expo アカウント / clone・`npm ci` / `npm start`                             | 無いとアプリが起動しない |
| **作る3章（B のみ）**     | VS Code / 拡張機能 / Prettier 設定 / SQLite CLI / `tsc`・`lint`・`test` / ブランチ運用 / 引き継ぎ資料 | 無くても起動はする       |

**同じ内容を作る2章と作る3章の両方に書かないこと。** 片方だけ直して食い違うのが、この手の手順書で一番よくある事故。

**着手前に境界を確定させること。** ここが揺れると両方書き直しになる。迷いやすいのは次の2つ。現状はどちらも作る3章側に置く想定。

- **Git の初回設定**（`user.name` / `user.email`）— clone するだけなら不要
- **VS Code 本体** — ソースを読むだけなら要らない

### 3.3. どこから何を持ってくるか

**担当ごとにどこを使うか、どこを使わないかは 2節の表にまとめてある。** 文章はそこから移すだけでよい。

節の中での対応は次のとおり。

| 作る章の節                     | 元のどこ                                             |
| :----------------------------- | :--------------------------------------------------- |
| 2章 Expo Go（アプリの導入）    | 元の 1.5 の**前半**                                  |
| 2章 Expo アカウント            | 元の 1.5 の**後半**                                  |
| 2章 ソース取得・依存導入・起動 | 元の 6章                                             |
| 3章 VS Code 拡張・Prettier 設定 | 元の 2章                                             |
| 3章 SQLite CLI とスキーマ検証  | 元の 1.4 と 7章                                      |
| 6章 トラブルシューティング     | 元の巻末の表から、**導入作業に関係するものだけ**抜く |

### 3.4. 決まっていること

| #   | 項目                 | 状態                     |
| :-- | :------------------- | :----------------------- |
| 1   | 開発ビルドを載せるか | **載せない**（決定済み） |
| 2   | 提出形式             | **Word・PDF に清書**     |

**1**: 開発ビルドの手順は書かない。`eas.json` が無く、iOS 実機ビルドには Apple アカウントも要る。**実際にビルドできない状態で手順だけ書いても再現できない**ため。
ただし黙って省略はしない。3章の末尾に、載せない理由と、そのせいで確認できない機能（**BGM のバックグラウンド再生・ロック画面**。ローカル通知は Expo Go でも確認できる）を書く。

**2**: Markdown で中身を確定させてから、最後に一気に清書する。**先に清書しない**（直すたびに崩れる）。

### 3.5. 書くときの最低限のルール

| #   | ルール                                                         | 理由                                                                                        |
| :-- | :------------------------------------------------------------- | :------------------------------------------------------------------------------------------ |
| 1   | バージョンは**実際に入れたもの**を書く（「最新版」と書かない） | 後から同じ物が手に入らなくなる                                                              |
| 2   | 各節の最後に**確認**（何が表示されれば成功か）を置く           | 無いと、失敗に気づかず次へ進む                                                              |
| 3   | **パスワード・個人のメールアドレスを書かない**                 | 提出物に平文で残る。**サンプル PDF は書いているが真似しない**（`docs/セキュリティ方針.md`） |
| 4   | 無い章は「なぜ無いか」を一文書く                               | 抜けたのか意図的かが伝わらない                                                              |

スクリーンショットは `docs/assets/導入手順書/` に置き、**ウィンドウ単位**で撮る。押すボタンを赤枠で囲み、ユーザー名などの個人情報は塗りつぶす。インストールは一度きりなので、**多めに撮って後で捨てる**。

サンプル PDF から真似するのは見た目だけ。**表紙 → 改訂履歴 → 目次の体裁**、**「No. / 項目 / 名称等」の3列表に画面キャプチャと操作を並べる形式**、**各節の最後に確認手順を置くこと**——この3つに限る。

### 3.6. 進め方

| #   | やること                                                              | 担当    |
| :-- | :-------------------------------------------------------------------- | :------ |
| 1   | 2章と3章の境界を確認する（3.2）                                       | 全員    |
| 2   | 文章を移す（スクショはまだ無くてよい）                                | A・B・C |
| 3   | まっさらな環境を用意する（別 PC、または Node / Git / VS Code を消す） | B・C    |
| 4   | インストールをやり直しながら画面を撮る。同時にメモを取る              | B → C   |
| 5   | 画像を貼り、操作内容を確定させる                                      | B・C    |
| 6   | 5章の動作確認を実際にやり、結果を書く                                 | C       |
| 7   | D がルート A を再現 → 詰まった所を6章に足し、手順を直す               | D       |
| 8   | D がルート B を再現 → 同上                                            | D       |
| 9   | 通し読み。目次・改訂履歴・日付を埋める                                | 全員    |
| 10  | Word・PDF に清書する                                                  | 全員    |

## 4. 提出前チェックリスト

| #   | 確認項目                                                         | 済  |
| :-- | :--------------------------------------------------------------- | :-- |
| 1   | バージョンが実際に入れたものになっている（「最新版」表記が無い） | ☐   |
| 2   | 各節に「確認」（何が表示されれば成功か）がある                   | ☐   |
| 3   | パスワード・個人情報・アカウント名が載っていない                 | ☐   |
| 4   | スクリーンショットの文字が読める                                 | ☐   |
| 5   | **書いた人以外が、2章だけでアプリを起動できた**（ルート A）      | ☐   |
| 6   | **書いた人以外が、2章＋3章で開発できる状態になった**（ルート B） | ☐   |
| 7   | 2章と3章で同じ導入を二重に書いていない                           | ☐   |
| 8   | 5章のチェックリストに結果が書かれている                          | ☐   |
| 9   | 6章に、実際に詰まった事象が書かれている                          | ☐   |
| 10  | 無い章の理由が書かれている（4章の DB、3章末の開発ビルド）        | ☐   |
| 11  | 改訂履歴・作成者・日付が埋まっている                             | ☐   |

**5 と 6 が通っていないものは未完成。**
